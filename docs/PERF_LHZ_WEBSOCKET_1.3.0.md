# LHZ.WebSocket 1.2.0 → 1.3.0 负载性能对比

> 测试日期：2026-11-04  
> 被测变更：`LHZ.WebSocket.AspNetCore` / `LHZ.WebSocket` 1.2.0 → 1.3.0（1.3.0 的核心变更是 frame buffer 池化，见 LHZ.WebSocket 提交 `43a84b1`，发布提交 `b67b9a3`）  
> 结论先行：**1.3.0 在库层明显更快、分配更少；但在这个应用的正常负载下没有可测出的容量提升**。帧解析只占单条消息处理成本的约 1%–3%，瓶颈在协议 JSON 序列化、Redis 在线状态续期和数据库写入。

## 1. 测试环境

| 项 | 值 |
|---|---|
| CPU | Intel i7-9700K，8 核 8 线程 |
| 内存 | 32 GB |
| OS | Windows 10/11（.NET 10.0.9 运行时） |
| 数据库 | PostgreSQL 16（Docker，127.0.0.1:55432） |
| 缓存 | Redis 7（Docker，127.0.0.1:56379） |
| 服务端 | `dotnet publish -c Release` 本地进程，`ASPNETCORE_ENVIRONMENT=Production` |
| 客户端 | 同机 .NET 10 `ClientWebSocket` 压测进程（不是 LHZ.WebSocket 客户端，避免同一实现互相抵消） |

服务端与压测客户端**同机**运行，且 Docker 中的 PostgreSQL/Redis 也占用 CPU。所有数字用于**版本间相对比较**，不代表生产环境的绝对容量。

## 2. 测试方法

### 2.1 库级基准

使用 LHZ.WebSocket 仓库自带的 `.perf` 基准（`Program.cs` / `NetworkBench.cs`），分别引用 NuGet 包 1.2.0 与 1.3.0，目标 `net10.0`，`TieredCompilation=false`。微基准为 3 次预热 + 7 次迭代，网络 echo 为 100 条预热 + 5 次迭代，均取中位数。覆盖同步/异步帧读取、帧创建、掩码、分片和本机 loopback echo。

### 2.2 应用级负载

把 OnlineChat 服务端源码分别以 1.2.0 / 1.3.0 发布（服务端业务代码完全相同），各用独立的 PostgreSQL 数据库与 Redis DB，关闭 FreeSql 的 SQL 控制台日志（Production 模式本身不输出），其余配置一致。

压测客户端为独立进程，使用 BCL `ClientWebSocket`：

- **心跳闭环**：96 条连接，每条收到 `pong` 后再发下一条，测 RTT；客户端在本机约 80k msg/s 处先到瓶颈。
- **心跳开环**：96 条连接 × 2100 条/秒 ≈ 201.6k 条/秒的报价速率，持续 15s，测服务端能吞下多少；客户端批量发送，避免每条消息一个定时器。
- **私聊**：两个用户（好友关系）、各 1 条连接，发送方 100 条/秒发 `private_message`，测发送方回显 RTT 与接收方送达延迟；每条消息都走数据库写入 + 推送。
- 每个场景先跑一次预热，再跑 3 次取中位数；服务端 CPU/Working Set 由压测进程按 200ms 采样 `Process` 计数器。表中“单核%”= 100% 为一个逻辑核，170% 约等于 1.7 个核。

> 注：应用级心跳每次都会触发 `IPresenceStore.RefreshAsync`（Redis 续期在线 TTL），这是应用自身的设计，不属于 WS 帧层。

## 3. 库级结果

单位：每帧耗时（ns）与每帧分配（B），中位数。

| 用例 | 1.2.0 | 1.3.0 | 变化 |
|---|---|---|---|
| 同步读 1 KB | 144.1 ns / 1112 B | 92.4 ns / 0.16 B | 时间 **-36%**，分配几乎归零 |
| 同步读 1 KB（masked） | 1288.8 ns / 1144 B | 223.7 ns / 0.16 B | 时间 **-83%**（约 5.8×） |
| 同步读 64 KB | 6654 ns / 65627 B | 3406.5 ns / 4.1 B | 时间 **-49%** |
| 异步读 1 KB | 220.0 ns / 1488 B | 181.7 ns / 88.5 B | 时间 -17%，分配 -94% |
| 异步读 64 KB | 6153 ns / 66009 B | 2493 ns / 98.7 B | 时间 **-59%** |
| 同步读 16 B | 41.9 ns / 72 B | 58.4 ns / 0.02 B | 小帧慢 39%（池化固定开销） |
| 创建 1 KB（无掩码） | 10.0 ns / 0 B | 40.5 ns / 0.04 B | 慢 4×：1.3.0 把 payload 拷进池化 buffer |
| 创建 1 KB（masked） | 1033.0 ns | 134.2 ns | **-87%**（约 7.7×） |
| 创建 64 KB | 10.3 ns | 1310.7 ns | 慢约 127×：1.2.0 只包裹调用方数组，1.3.0 要拷贝 64 KB |
| 网络 echo 1 KB | 122411 msg/s；5317 B/msg | 173067 msg/s；3182 B/msg | **+41%** 吞吐，**-40%** 分配 |
| 网络 echo 16 KB | 26403 msg/s | 42938 msg/s | **+63%** |
| 网络 echo 64 KB | 6760 msg/s | 10719 msg/s | **+59%** |

**解读**：

- 1.3.0 的池化/span 改造把读取路径的分配从“每帧一个数组”降到接近零，masked 路径（客户端上行帧必须掩码）提升最大。
- 创建路径变慢是**有意的取舍**：1.2.0 直接改写调用方数组（零拷贝但会污染调用方），1.3.0 拷进池化 buffer。小消息多花几十 ns，64 KB 大帧的拷贝成本被放大；但端到端 loopback 仍快 41%–63%，因为接收侧省得更多。
- 对本应用来说，WS 消息是几百字节的 JSON，创建路径的几十 ns 相对整条链路可以忽略。

## 4. 应用级结果

### 4.1 心跳闭环（96 连接，15s，3 次中位数）

| 指标 | 1.2.0 | 1.3.0 | 变化 |
|---|---|---|---|
| 吞吐 | 83,934 msg/s | 85,925 msg/s | +2.4% |
| RTT p50 | 0.919 ms | 0.901 ms | -2.0% |
| RTT p95 | 2.332 ms | 2.259 ms | -3.1% |
| RTT p99 | 3.942 ms | 3.833 ms | -2.8% |
| 服务端 CPU（单核%） | 193.8% | 217.7% | +12.3% |
| 服务端峰值 WS | 211 MB | 204 MB | -3.4% |

闭环测试客户端先到瓶颈（96 条连接也只跑到 ~80k msg/s；开环能到 193k），所以这里的 CPU 差异主要反映客户端反压下的批处理节奏，不应单独解读为回归。

### 4.2 心跳开环（96 连接 × 2100/s ≈ 201.6k/s 报价，15s，3 次中位数）

| 指标 | 1.2.0 | 1.3.0 | 变化 |
|---|---|---|---|
| 实际吞吐 | 193,264 msg/s | 193,248 msg/s | 0.0% |
| 发送/收到 | 2,900,562 / 2,900,562 | 2,899,680 / 2,899,680 | 全部送达 |
| 服务端 CPU（单核%） | 170.2% | 173.8% | +2.1% |
| 服务端峰值 WS | 230.1 MB | 236.5 MB | +2.8% |

这是最能说明问题的对照：**在相同报价负载下，两版吞吐完全一致，CPU 与内存差异在 3% 以内**。1.3.0 的帧层优化被应用层的其他成本淹没了。

### 4.3 私聊（100 条/秒，20s，3 次中位数）

| 指标 | 1.2.0 | 1.3.0 | 变化 |
|---|---|---|---|
| 发送/回显/送达 | 1953 / 1953 / 1953 | 1952 / 1952 / 1952 | 全部成功 |
| 回显 RTT p50 | 6.81 ms | 7.47 ms | +0.66 ms |
| 回显 RTT p95 | 8.92 ms | 9.06 ms | +0.14 ms |
| 回显 RTT p99 | 10.73 ms | 10.26 ms | -0.47 ms |
| 服务端 CPU（单核%） | 17.4% | 15.5% | -10.9% |
| 服务端峰值 WS | 158 MB | 157 MB | -0.6% |

p50 的 +0.66 ms 出现在数据库写入占主导的路径上，而 p99 反而略低；两个版本使用独立的 PostgreSQL 数据库，WAL/checkpoint 与缓存状态不同，这个量级判断为数据库侧噪声，不能归因于 WS 帧层。

### 4.4 过载观察（480k/s 报价，10s，非稳态）

| 指标 | 1.2.0 | 1.3.0 |
|---|---|---|
| 客户端发出 | 3.67M | 3.84M / 3.56M |
| 服务端回包 | 80k（2.2%） | 1.22M（32%）/ 2.22M（62%） |
| 服务端 CPU（单核%） | 114% | 90% / 149% |
| 服务端峰值 WS | 758 MB | 651 MB / 3006 MB |

这是**合成过载**，两版都失去了端到端背压，不能当作生产结论。但它暴露了一个行为变化：

- 1.3.0 修复了 `Send()` 在出站队列满时抛 `InvalidOperationException` 的问题，改为等待 `ValueTask`；
- 1.2.0 在队列满时“抛异常 → 应用层捕获并丢弃”，所以内存低、但大量回包丢失；
- 1.3.0 改为等待后，应用层 `_ = _dispatcher.DispatchAsync(...)` 的 fire-and-forget 与库内出站队列会一起堆积未释放的帧（本次无法区分两者占比），过载时内存显著抬升（本次观察到 0.65–3.0 GB，压测结束后短时间内仍保持数 GB，未等到完全排空）。

结论不是“1.3.0 更差”，而是：**升级把过载时的“丢消息”换成了“堆积内存”，如果应用层没有有界队列/并发限制，峰值流量下需要重点观察 Working Set。** 正常 200k/s 负载下没有这个现象（230 MB 左右，3 次运行稳定）。

> 另外，1.3.0 冷启动后的第一次 288k/s 运行出现过只收到 49k/2.67M 回包的异常，预热后恢复正常；压测必须包含预热轮次。

## 5. 为什么应用层看不到提升

应用级心跳每条的 CPU 成本约为：

- 1.2.0：193k msg/s 时 1.70 核 → **约 8.8 µs/条**
- 1.3.0：193k msg/s 时 1.74 核 → **约 9.0 µs/条**

而库级 1 KB 帧读取只要 0.09–0.14 µs，掩码约 0.22 µs。帧层占比约 1%–3%（掩码帧约 2.5%）。每条心跳的主要成本是：

1. `LHZ.FastJson` 反序列化 `WsMessage`；
2. `IPresenceStore.RefreshAsync` 每次心跳续期 Redis TTL；
3. 序列化并发送一个约 190 B 的 `pong`；
4. 每连接一个接收循环、异步调度。

这些都不在 1.3.0 的优化范围内，所以吞吐不变是预期结果。

## 6. 结论与建议

1. **升级本身安全**：正常负载下吞吐、p50/p95/p99、内存均在噪声范围内，没有回归信号。
2. **不要指望升级带来容量提升**：该应用 WS 路径的瓶颈是 JSON + Redis presence + 数据库，不是 RFC 6455 帧层。要提升容量，优先优化这几处，而不是继续换 WS 库。
3. **升级的收益在别处**：
   - 读取不再每帧分配数组，GC 压力显著下降（大帧/高连接数时更明显）；
   - masked 帧快 4–8×，对大上行流量有意义；
   - 64 KB 级帧读取快约 2–2.5×，loopback echo 快约 1.6×。
4. **过载行为需要防护**：1.3.0 在出站队列满时等待而非抛异常，建议给 `DispatchAsync` 加有界并发/队列，或在压测中验证目标峰值下的 Working Set；否则极端过载可能从“丢消息”变成“内存上涨”。
5. 大帧创建变慢是设计取舍：如果将来有大的二进制下行帧，单独基准 1.3.0 的 `CreateDataFrame` 路径，不要只看小 JSON 的结果。

## 7. 复现要点

库级：

```bash
# 在 LHZ.WebSocket 仓库的 .perf 下，分别以 NuGet 1.2.0 / 1.3.0 建立两个 net10.0 控制台工程
# 引用 Program.cs + NetworkBench.cs，1.3.0 侧定义 LOCAL（Data 为 span、frame 需 Dispose）
dotnet run -c Release
```

应用级：

```text
1. 以 1.2.0 / 1.3.0 分别 dotnet publish OnlineChat.Server（同一份业务代码）
2. 准备独立 PG 数据库 + 独立 Redis DB；Production 模式启动（避免 SQL 控制台日志）
3. 造 2 个好友用户；为发送方创建 96 个独立登录会话（token 的 sid 必须互不相同，
   否则 WsConnectionManager 会关闭旧连接）
4. 心跳开环：96 条连接，每条约 2100 条/秒，持续 15s；记录服务端 Process CPU/WorkingSet
5. 私聊：发送方 100 条/秒，持续 20s；消息 ID 用客户端生成，按 ID 匹配回显/送达
6. 每场景先预热一轮，正式跑 3 轮取中位数
```

本次使用的压测客户端与库级工程放在系统临时目录，未提交进仓库；如需长期回归，可整理为 `backend/perf` 下的独立工程。

## 8. 局限

- 服务端、压测客户端、PostgreSQL、Redis 同机，CPU 互相争抢；绝对吞吐低于独立部署。
- 客户端是 BCL `ClientWebSocket`，不是浏览器/移动端；浏览器端的连接建立、TLS、代理开销未覆盖。
- 心跳是合成负载，不是真实聊天流量分布；私聊只覆盖 2 人、100 条/秒。
- 两个版本使用不同数据库，私聊延迟的 ±0.7 ms 属于数据库侧波动。
- 过载测试的 480k/s 超过服务端稳定容量，只用于观察退化行为，不作为容量指标。
