## 零、修复后发现并已修正的一个回归（重要）

**症状**：注册/找回密码时输入邮箱验证码，**永远**返回「验证码错误或已过期」。

**根因（我上一步引入的）**：在 `SendVerificationCodeHandler` 里把两种情况当成了同一种——

```csharp
// 错误写法：只要没发出去就作废验证码并报错
if (!sent && !_env.IsDevelopment)
{
    await _codes.RemoveAsync(email, ct);   // ← 把刚存下的验证码删了
    throw new DomainException("验证码发送失败，请稍后重试");
}
```

你们的部署恰好同时满足两个条件：**`ASPNETCORE_ENVIRONMENT=Production`**（compose 里写死）且
**`SMTP_HOST` 为空**。于是每次发码的流程是：

1. `SaveAsync` 把验证码写进 Redis；
2. `EmailSender` 发现未配置 SMTP → 把验证码**打印到服务器日志**后返回 `false`；
3. 上面对 `false` 的处理**把那条验证码删掉**；
4. 运维从日志读到码 → 提交 → Redis 里已经什么都没有 → `stored.IsNullOrEmpty` → 「验证码错误或已过期」。

删除发生在保存之后、且每次发码都会重演，所以**无论重试多少次都不可能成功**。

**修法**：区分「未配置 SMTP」与「已配置但发送失败」这两个语义完全不同的分支 ——
给 `IEmailSender` 加了 `IsConfigured`：

| 情况 | 处理 |
|---|---|
| 已配置且发送成功 | 正常返回，不回传验证码 |
| **未配置 SMTP**（受支持的运行模式） | **保留验证码**（运维从日志取码仍可用）；生产环境**不回传**验证码，开发环境回传（本地调试）；返回说明性提示 |
| 已配置但发送失败 | 作废验证码**释放 60 秒冷却**并报错，让用户能立刻重试 |

守住的底线不变：**任何情况下都不在生产环境回传验证码**（那才是原先的账号接管漏洞）。

另外补了一条生产环境启动告警：未配置 SMTP 时明确提示「验证码只输出到服务器日志，不会发送邮件」——
原来的日志措辞是「（开发模式）」，而生产环境同样走这条路径，会把排查方向带偏。

**验证方式**：这一项是在**你们正在运行的 Docker 栈上做端到端验证**的，不只是单元测试：

```
send-code  → {"success":true,"message":"验证码已生成，但当前未配置邮件服务，请联系管理员从服务器日志获取",
              "data":{"devCode":null,"cooldownSeconds":60}}     ← 成功，且不泄露验证码
日志取码    → ...dsh-e2e-71489@test.local -> 166402
错误验证码  → {"success":false,"message":"验证码错误或已过期"}    ← 拒绝路径仍然正确
日志里的码  → {"success":true,"message":"注册成功，你的账号是 10000，请牢记"}  ← 修复前必失败
```

验证期间创建的测试账号已从数据库清理（清理后确认 `User_` 表为空，账号序列重启时已重置回 10000）。

对应回归测试：`生产环境未配置SMTP时验证码仍然有效`；
并把 `FakeEmailSender` 的「是否配置」与「是否发送成功」拆成两个独立开关 ——
合成一个 bool 正是这个 bug 得以溜过的原因。

## 三、几处值得说明的实现选择

### 群组准入用「默认收紧 + 显式开放」，而不是删掉加入功能

`GroupJoinPolicy` 默认 `InviteOnly`。这保留了「按群 ID 加入」这个产品能力，但把决定权交回群主：需要公开招募的群由群主调 `PUT /api/groups/{id}/join-policy` 显式开成 `Open`。存量群在补列时取默认值 0，即**升级时一并收紧**——这是安全的方向。

校验顺序也有讲究：先判「已是成员」，再判「是否开放」。反过来会让群主点自己已加入的群时报「该群仅限邀请」，提示错误。

### `DevCode` 门控之外，顺手释放了冷却窗口

生产环境发送失败时抛错，同时调 `IVerificationCodeStore.RemoveAsync` 把已存的验证码删掉。不删的话，那次「没发出去的发码」会占满 5 分钟冷却，真实用户只能干等。这是一个容易被忽略的连带问题。

### 启动自检做成「失败即拒绝启动」

`AppSettings.EnsureProductionReady()` 在生产环境校验 JWT 密钥（长度 + 是否仍是仓库默认值）、连接串、`Robot__TokenKey`，不合格就抛异常终止。理由写在代码注释里：这几项都写在仓库里，静默降级等于没有防护，而部署时立刻报错是最便宜的发现方式。

### WS 新增事件沿用了既有「让客户端退出会话」的语义

`group_removed` 与既有的 `group_dissolved` 处理完全一致（提示 + 刷新列表 + 若正在该会话则关闭）。新增 `friend_removed` 则额外在「正在与对方私聊」时关闭会话。

### 前端 `sendMessage` 改为返回 `boolean`

这是必须的：聊天区先把消息乐观插进列表，若发送静默失败，那条消息会永远停在「发送中」。同时给心跳加了 pong 超时——半开连接（TCP 未断但对端不可达）此前检测不到。

### 一条 SQL 形状测试

`MessageQueryOrderingTests` 用 FreeSql 的 `ToSql()`（不需要真实数据库）断言生成的 ORDER BY 同时含 `SentAt` 与 `Id`。它顺带验证了「多次调用 `OrderBy` 是追加而非覆盖」这一 FreeSql 行为——这正是我改动时的不确定点，所以用测试钉住而不是靠记忆。

## 四、部署相关的行为变化（会影响到现有部署）

1. **四个变量变为必填**：`POSTGRES_PASSWORD`、`JWT_SECRET`、`ROBOT_TOKEN_KEY`、`REDIS_PASSWORD`，缺失即 `docker compose` 报错。Redis 开启 `requirepass`。
2. **PG/Redis 端口只绑 `127.0.0.1`**，管理后台容器改为非特权 nginx 并监听 8080（主前端反代目标已同步改为 `frontend-admin:8080`）。
3. **群组默认收紧为仅限邀请**（见 §三）。
4. **会创建 10 条唯一索引 + 一批二级索引**；存量数据有重复时唯一索引会创建失败，服务照常启动但只记警告、约束暂不生效。

以上四点已写入 [DEPLOY.md](docs/DEPLOY.md) 的「从旧版本升级时的三处行为变化」与「部署拓扑」小节。

## 五、有意延后的 5 项及理由

| 项 | 为什么这一轮不动 |
|---|---|
| **WebSocket 令牌仍走查询串**（`?access_token=`） | 正确修法是短时一次性 ticket（新增 `/api/auth/ws-ticket` + Redis 单次使用票据 + 握手改造）。这是**鉴权路径的重写**，而本机无法启动服务验证握手 —— 改错了就是全站实时通信不可用。已做的缓解：nginx 对 `/ws` 用不含查询串的 log_format、后端异常日志脱敏。**建议在能跑起来的环境里单独做这一项。** |
| **多实例部署（Redis pub/sub 背板）** | 连接表在进程内存，跨实例广播需要架构改造，且必须有多个实例才能验证。已在 DEPLOY.md 明确写「只支持单实例」并说明多开会坏在哪里、要改什么。 |
| **管理后台刷新令牌** | 后端没有 `/api/admin/auth/refresh`，也就没有刷新令牌可发。前端已把刷新链路写好并在拿到 `refreshToken` 时启用，属于「后端补一个端点即可激活」的状态。这是功能缺失，不是缺陷。 |
| **上传文件的魔数嗅探** | 现有防护是扩展名白名单 + GUID 文件名 + `nosniff`。补魔数校验要读流头部、涉及流位置与大小限制的配合，同样是无法在本机验证的 I/O 路径。 |
| **仪表盘约 47 次往返 / 会话列表每群一次未读计数** | 纯性能优化，不改变正确性；且需要真实数据量才能判断改动是否值得（很可能应该改成一次聚合查询，但那要连同响应结构一起动）。已在上一轮报告中记录。 |

此外，`DomainEventOutbox` 内部是普通 `List`（非线程安全）：目前所有命令内都是顺序 await，没有并发派发路径，因此安全；但这是一个**隐性约束**，将来若在命令里并发派发事件会踩到。已在代码注释中保留说明。

## 七、总体判断

这一轮把上一轮报告里的**可利用性问题全部关掉了**：群组越权、验证码泄露、凭据入库、限流缺口、僵尸连接、越权读名单。同时补齐了消息校验、幂等发送、缺失的领域事件通知，以及前端那条从没接上的刷新令牌链路。

改动量不小（74 个文件），但每一处都伴随着一个能跑起来的验证：**936 个测试、0 警告、两个前端构建通过、compose 正反两向验证**，验证码那条链路更是直接在运行中的 Docker 栈上跑了完整注册流程。新增的测试不是补覆盖率数字，而是逐条钉住「修复前的行为会失败、修复后的行为通过」——例如群组默认拒绝自行加入、生产环境发送失败不回传验证码、未配置 SMTP 时验证码仍然有效、同一客户端消息号只落一行、被踢出群会推送通知。

剩下 5 项延后都有一个共同特征：**它们的正确性无法在没有运行环境的情况下验证**。在鉴权路径、分布式广播、上传 I/O 上做「看起来对」的改动，风险高于收益。建议在有 Docker 与数据库的环境里逐项推进，而不是继续在静态检查下堆代码。
